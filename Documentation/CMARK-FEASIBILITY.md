# Direct cmark-gfm feasibility spike

Status: experimental, not a production adapter or a release qualification. Tested 2026-11-13 on Debian 13 x86_64, Swift 6.4.2, swift-cmark `437611671145d47e6d9679761b8a5987766f4ae5`, swift-markdown `ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a`, CommonMark cmark 0.31.2 `eec0eeba6d31189fd828314576494566d539b1e3`. No fork or upstream code modification was made.

## Findings

* `Experiments/CMarkProbe` links the unmodified swift-cmark products directly at an exact revision. Its single-threaded HTML executable creates a parser without extensions for the CommonMark experiment, and enables `table`, `strikethrough`, `tasklist`, `autolink`, and `tagfilter` for the GFM experiment. It enables parser source-position tracking, disables smart punctuation and enables raw HTML via `CMARK_OPT_UNSAFE` for specification comparison. The unsafe output is not a sanitizer or a host security policy.
* Direct access and independent extension selection work, but **this revision is not sufficient for the strict gates unchanged**. The CommonMark 0.31.2 output comparison passes 641/652, fails 11, skips 0. Of those 11, nine have the same XML tree structure as official cmark 0.31.2 when source positions are ignored, but different HTML: cmark-gfm collapses nested strong tags. The inspected `src/html.c` explicitly suppresses a `strong` tag when its parent is also `strong`; removing or configuring that behavior is a candidate renderer fix, not a validated patch. Two have different XML structures: the eight-digit decimal character reference (28) and Unicode punctuation/flanking (354). The inspected `src/houdini_html_u.c` admits eight digits, while the pinned CommonMark expectation requires treating this case as literal text. XML equivalence is a useful diagnostic, not proof of complete AST equivalence.
* The source-position sequences differ for seven of the nine structurally matching cases. For `****foo****`, the inner strong node is `1:1-1:11` in the direct cmark-gfm XML and `1:3-1:9` in official cmark's XML. These are cmark XML source positions, not an independent proof that either range is correct in every interpretation, or that Swift Markdown's ranges are lossless.
* With five extensions enabled, the fixed GFM exploratory subset passes 13/19, fails 6, skips 0. The six comprise published examples 279, 280, 324, 634, 635 and project interaction `interaction-tasklist-strikethrough-1`. The task-list failures are raw HTML serialization differences; a supplementary HTML-token diagnostic agrees for those cases. The entity and XMPP output differences require parser/behavior investigation. The 19 cases are not the complete GFM corpus.
* `Experiments/MarkdownProbe` uses the public Swift Markdown `Document(parsing:options:)` with `.disableSmartOpts` and `HTMLFormatter`. Against the same official CommonMark examples, it passes 481/652, fails 171, skips 0. Its fixed GFM subset passes 9/19, fails 10, skips 0. These are combined parser-and-formatter observations, not 171 proven parser bugs.
* Swift Markdown's tree, without source location annotations, is identical for `- a\n- b\n` and `- a\n\n- b\n`; its formatter outputs paragraphs for both. The cmark XML distinguishes `tight="true"` from `tight="false"` and its HTML differs accordingly. The inspected converter constructs its list nodes without preserving cmark's tightness flag; the public AST therefore does not directly retain that distinction. Source ranges plus original source may allow a separate inference, but that is not equivalent to preserving the flag across arbitrary transformations.
* Swift Markdown's parser produces a `Text` node for `Visit www.commonmark.org.`, whereas the direct GFM parse contains a link node. This follows from its currently attached extensions and demonstrates that exposing its default parse as a strict GFM AST would misrepresent that example. The Swift Markdown converter is internal; a separately configured cmark tree cannot be passed to it through a documented public conversion API. Further work is needed to establish precisely what a public AST projection can preserve; we have not surveyed all constructs.
* A separate Swift 6 concurrency stress executable performed 2,000 parallel independent parser allocations and renders (half CommonMark-shaped, half strikethrough-enabled), with 0 mismatches. Core extension registration uses cmark's once primitive. This small stress check does **not** prove general thread safety, cancellation, bounded memory, or safe concurrent sharing of a parser/tree.
* The direct-cmark experiment resolves an exact revision in its own `Package.resolved`. A separate experiment with Swift Markdown uses its transitive `gfm` branch pinned in that executable's lockfile. A direct exact swift-cmark requirement conflicts with Swift Markdown's `gfm` branch requirement in SwiftPM. A library's consumers resolve their own dependencies, so the experiment's lockfile is not a general downstream guarantee.
* Static archives of official cmark 0.31.2 and the inspected cmark-gfm have 103 shared exported `cmark_` symbol names (`nm -g --defined-only`, Linux). Linking both unmodified into one process may cause collisions or symbol interposition and needs a deliberate symbol-namespace/linkage design. This observation alone is not a complete platform linker analysis.

## Architectural implication

Keep the production API unimplemented while evaluating two concrete approaches: (1) narrowly fix or upstream the verified parsing, serialization and source-range differences in the cmark-gfm path, with explicit profile settings and a safe AST conversion boundary; or (2) use independently qualified reference implementations behind an internal interface, resolving shared C symbols and representing any AST data the Swift Markdown public model cannot preserve. Neither approach is yet proven to satisfy all GFM behavior or downstream SwiftPM resolution. A fork is not yet justified: the smallest necessary upstream changes depend on choosing and measuring one path. Do not present Swift Markdown's existing formatter or a reparsed default document as the strict result.

## Reproduction

Build the pinned references with `Tools/build-references.sh "$PWD/.references"`. With Swift 6.4.2 on PATH:

```sh
swift build --package-path Experiments/CMarkProbe --disable-automatic-resolution -j 4
swift build --package-path Experiments/MarkdownProbe --disable-automatic-resolution -j 4
Experiments/CMarkProbe/.build/debug/cmark-stress
python3 Tools/conformance.py commonmark --renderer-version 'swift-cmark 437611671145d47e6d9679761b8a5987766f4ae5 via CMarkProbe' --report Artifacts/cmark-probe-commonmark.json -- "$PWD/Experiments/CMarkProbe/.build/debug/cmark-probe" commonmark
python3 Tools/conformance.py gfm --view fixed --renderer-version 'swift-cmark 437611671145d47e6d9679761b8a5987766f4ae5 via CMarkProbe' --report Artifacts/cmark-probe-gfm-fixed.json -- "$PWD/Experiments/CMarkProbe/.build/debug/cmark-probe" gfm
python3 Tools/conformance.py commonmark --renderer-version 'swift-markdown ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a HTMLFormatter' --report Artifacts/markdown-probe-commonmark.json -- "$PWD/Experiments/MarkdownProbe/.build/debug/markdown-probe" html
python3 Tools/conformance.py gfm --view fixed --renderer-version 'swift-markdown ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a HTMLFormatter' --report Artifacts/markdown-probe-gfm-fixed.json -- "$PWD/Experiments/MarkdownProbe/.build/debug/markdown-probe" html
python3 Tools/compare_cmark_xml.py --html-report Artifacts/cmark-probe-commonmark.json --reference "$PWD/.references/cmark-build/src/cmark" --probe "$PWD/Experiments/CMarkProbe/.build/debug/cmark-probe" --report Artifacts/cmark-probe-xml-differences.json
```

Nonzero conformance command exits are expected when cases fail. The probe supports `xml-commonmark` and `xml-gfm` for inspection; MarkdownProbe supports `tree`. The SwiftPM experiments pin their checked-in lockfiles; the source packages are fetched from their official repositories. The probe uses default cmark allocation, frees each parser, tree and renderer buffer, and runs no production-wide policy. Its behavior has not been tested on macOS. No benchmark, malformed-input test, cancellation test, or resource-bound guarantee has been performed.

## Full published GFM diagnostic for Swift Markdown

A later diagnostic ran the unchanged Swift Markdown parser and `HTMLFormatter`, with `.disableSmartOpts`, once per case across all 677 extracted published GFM examples: 489 exact HTML matches, 188 differences, 0 skips. Reproduce with:

```sh
python3 Tools/conformance.py gfm --renderer-version 'swift-markdown ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a; disableSmartOpts; HTMLFormatter' --report Artifacts/markdown-probe-gfm-published-diagnostic.json -- "$PWD/Experiments/MarkdownProbe/.build/debug/markdown-probe" html
```

This is a diagnostic, not an official GFM conformance percentage: the published corpus mixes base and extension examples that may need different reference configurations, the extraction has not been independently verified against the exact page source, and this combines parsing and rendering. The previously documented fixed-profile subset provides more targeted evidence but covers only 19 cases, including two project-authored interactions. Concrete extension examples in the diagnostic include passing table example 198 and strikethrough example 491, and failing extended-autolink example 629, tag-filter example 657, and task-list HTML example 279. A task-list HTML mismatch alone does not prove that the task marker was parsed incorrectly.
