# Pure Swift parser and renderer: initial options assessment

Assessment 2026-11-13. This is research, not an architecture decision. Pure Swift changes the original brief's preference for using a mature reference parser rather than implementing CommonMark; it would need to become an explicit project goal. No code was imported and no licensing or performance audit was completed.

## Candidates inspected

* [Swift MarkdownKit](https://github.com/objecthub/swift-markdownkit/tree/1fdcb40c5c49c643b4224937d90978c2ce21aa8c): native Swift, Apache-2.0; source has block/inline parsers and Swift AST and HTML generators. README claims all 652 CommonMark 0.31.2 examples pass **with output normalization**, not our byte-exact gate. It explicitly says Linux is unsupported and its extended dialect differs from GFM: single tilde means underline, extended autolinks are absent, and its table syntax has additional behavior. The complete package failed to build on Debian Linux with Swift 6.4.2 (`no such module UIKit`). Its Swift 6 `Sendable` design uses `@unchecked` for open classes; independent concurrency validation is still needed. Potentially valuable parser-source candidate if a portable core can be isolated; isolation, its dependencies, source-range behavior and baseline exact output have not been proven.
* [swiftlang/swift-markdown](https://github.com/swiftlang/swift-markdown/tree/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a): useful Swift AST, visitors, walkers and rewriters, but its existing parser uses C and its AST lacks list tightness. Extracting the Swift infrastructure retains engineering and maintenance costs; it does not supply a pure-Swift parser. Review Apache license, Swift runtime exception and all file notices before copying.
* [comrak](https://github.com/kivikakk/comrak/tree/a517526621b9e15f925a89e0abadc8d03521b377): Rust, BSD-2-Clause according to Cargo.toml. README advertises CommonMark 652/652 and GFM 670/670 against linked suites, but explicitly says the GFM tagfilter extension was removed, and its GFM mode can enable output quirks. These are upstream claims, not runs by us or proof against our pinned published corpus and strict output contract. Its arena AST and parser are a useful study/differential reference; a port has considerable verification and ongoing maintenance cost.
* [markdown-rs](https://github.com/wooorm/markdown-rs/tree/1506572f9b406431402928f3a8b3df0b4ae2d8f5): Rust, MIT; upstream claims CommonMark/GFM coverage and documents an event/state-machine architecture with HTML and AST outputs. Not independently qualified here. A valuable second architecture/reference to evaluate, not a verified source of our exact profile behavior.
* [pulldown-cmark](https://github.com/pulldown-cmark/pulldown-cmark/tree/1c1a3123207d9e07fdfcf3d3418a047907185afb): Rust, MIT; pull events and source offsets are attractive patterns. Its README states a CommonMark conformance goal and lists selected GFM extensions. We did not establish full GFM/tagfilter or exact HTML support; do not assume it. It is not pure Swift and a port is a separate project.
* [Ink](https://github.com/JohnSundell/Ink/tree/bcc9f219900a62c4210e6db726035d7f03ae757b): Swift/MIT, but README explicitly says it does not fully support CommonMark. Not an attractive starting point for strict compatibility without substantial work.

## Tentative recommendation

Run a bounded, measured feasibility comparison before selecting code: (1) isolate an unmodified portable MarkdownKit parser/HTML core if feasible; run our raw 652 CommonMark examples and GFM corpora on Linux, plus concurrency and performance tests; (2) investigate whether a compatible Swift Markdown AST projection is possible without losing required metadata; (3) compare MarkdownKit's results and maintenance cost with a minimal independently designed pure-Swift implementation, informed by cmark, comrak, markdown-rs and pulldown-cmark. Keep pinned official C references and the existing exact-output harness as development-only oracles.

Do not pick a whole-codebase port or commit to Swift Markdown AST reuse before those experiments. The current evidence does not establish that the MarkdownKit core is portable in isolation, faster, or capable of strict GFM, nor that any Rust project's advertised counts meet our exact byte comparison. Direct translation of source creates a derivative work: retain notices and honor each applicable license, including third-party bundled assets if included. Avoid importing unrelated Apple UI, JavaScript resources, or application dependencies into a Linux parser core.

A promising design is per-parse local mutable state over owned UTF-8 source, explicit block/reference resolution and inline parsing, byte offsets with documented source mapping, faithful list and link metadata, and a separate deterministic renderer. A pull/event interface can supplement an optional AST; references may require buffering or multiple passes, so do not promise one-pass constant-memory streaming without proof. Make profile settings explicit and independent. Public `Sendable` ownership should avoid sharing mutable parser state; parallelize independent documents and only support cancellation/budgets where checked. Evaluate `Span`/`InlineArray` for measured hot paths and lifetime/platform constraints rather than assuming they improve throughput. Benchmark optimized builds with representative documents, pathological inputs, allocations, memory, tail latency and throughput; conformance, fuzzing and differential tests precede optimization.

The GFM 677 published examples and upstream's per-example extension suites do not currently define one verified all-features-on 677/677 gate. Preserve raw fixtures, make configurations and unresolved cases explicit, and do not call a subset full conformance. No library discussed here has been demonstrated by us to satisfy the complete pure-Swift, Linux, byte-exact CommonMark plus GFM objective.
