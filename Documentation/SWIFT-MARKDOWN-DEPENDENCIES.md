# What Swift Markdown delegates to C

Inspected 2026-11-13: swift-markdown [`ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a`](https://github.com/swiftlang/swift-markdown/tree/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a) and the `gfm` branch of swift-cmark [`437611671145d47e6d9679761b8a5987766f4ae5`](https://github.com/swiftlang/swift-cmark/tree/437611671145d47e6d9679761b8a5987766f4ae5). On that date both matched the respective upstream HEAD/branch. `swift-markdown` uses a moving `gfm` branch dependency, so consumers must inspect their resolved revision.

## Production dependencies

The [`Markdown` target](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Package.swift#L24-L31) depends directly on `cmark-gfm` and `cmark-gfm-extensions`, products of [swiftlang/swift-cmark](https://github.com/swiftlang/swift-cmark/blob/437611671145d47e6d9679761b8a5987766f4ae5/Package.swift). Their `src` and `extensions` targets compile C source as part of the package. This is production code used during parsing, not just a test fixture or build-time generator. It executes in-process through Swift/C interop; Swift Markdown does not shell out to a cmark executable and does not require Ruby. How it is linked depends on the consumer's build.

The package also includes a small C target, [`CAtomic`](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Sources/CAtomic/CAtomic.c), used by Swift's atomic unique-ID counter. It is not the Markdown parser. `swift-docc-plugin` appears in the standalone package manifest for documentation tooling, not as the `Markdown` target's parser dependency.

## Ordinary parsing

1. The public Swift [`Document(parsing:)`](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Sources/Markdown/Base/Document.swift#L38-L50) sends ordinary input to the Swift `MarkupParser`.
2. The Swift [`CommonMarkConverter.swift`](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Sources/Markdown/Parser/CommonMarkConverter.swift#L417-L435) imports the C modules, registers the core extensions, creates a C parser, attaches selected extensions, feeds the source and finishes the parser. cmark handles standard block and inline recognition, references, entity handling and extension parsing. See C [`blocks.c`](https://github.com/swiftlang/swift-cmark/blob/437611671145d47e6d9679761b8a5987766f4ae5/src/blocks.c), [`inlines.c`](https://github.com/swiftlang/swift-cmark/blob/437611671145d47e6d9679761b8a5987766f4ae5/src/inlines.c), and [`references.c`](https://github.com/swiftlang/swift-cmark/blob/437611671145d47e6d9679761b8a5987766f4ae5/src/references.c).
3. The converter walks the C tree and constructs Swift Markdown nodes, copying literals, destinations, titles, checkbox states, table data and source positions where supported. See [`createContainer`](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Sources/Markdown/Parser/CommonMarkConverter.swift#L322-L413) and its [source-range conversion](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Sources/Markdown/Parser/CommonMarkConverter.swift#L155-L180). Not every cmark distinction is preserved; in particular, the current list conversion does not copy list tightness.
4. After conversion, the Swift code frees the C iterator, C tree and C parser. The returned public `Document` consists of Swift Markdown markup structures; it is not simply a live C node pointer.

The optional Swift block-directive parser is a genuine Swift parsing layer for directives and associated features. It calls back into `MarkupParser`/cmark for ordinary Markdown line runs; enabling directives does not replace cmark with a complete Swift CommonMark parser. See [`BlockDirectiveParser.swift`](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Sources/Markdown/Parser/BlockDirectiveParser.swift#L681-L706).

## Dialect and rendering

The pinned converter attaches **table, strikethrough and tasklist**. It registers the core extensions, but does **not** attach autolink or tagfilter to its parser. It enables `CMARK_OPT_TABLE_SPANS`, smart punctuation unless `.disableSmartOpts` is set, and source-position tracking unless disabled. [`ParseOptions`](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Sources/Markdown/Parser/ParseOptions.swift) does not expose a full CommonMark/GFM extension-selection API. Consequently, the C library's available features and the features actually enabled by Swift Markdown are different things.

Swift Markdown's [`HTMLFormatter`](https://github.com/swiftlang/swift-markdown/blob/ea1d88be47afe8a731b3971d7b3fb7a3a6db1a5a/Sources/Markdown/Walker/Walkers/HTMLFormatter.swift#L38-L63) is a **Swift** `MarkupWalker` over the Swift tree. It does not call cmark's C HTML renderer. The C library also has an independent HTML renderer (`src/html.c`), which our direct-cmark experiment used; results from that renderer must not be attributed to Swift's `HTMLFormatter`. Swift Markdown also supplies Swift visitors, walkers, rewriters and a Markdown formatter.

The architecture is therefore hybrid: C parser and syntax extensions; Swift conversion and public AST; Swift traversal, editing and formatters. The cmark dependency can affect parsing semantics and source ranges; conversion can preserve or lose metadata; the Swift formatter independently determines final HTML. All three boundaries need separate qualification. Swift Markdown's own README says its parser is powered by cmark-gfm and notes that its effective dialect may change.
